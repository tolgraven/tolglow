# Native MetalFX Room scaling probe

This standalone macOS tool compares a Metal full-screen bilinear sample with MetalFX SpatialScaler over identical resident color textures. It separates a scaler’s cost from scene rendering and texture transfers. Both renderers receive the same two analytic frames of eight thin shafts and volumetric-looking color gradients. The synthetic bilinear pass controls for the linear texture sample used by the current Film pass. The issue tracks the eventual mounted Room comparison. [Tolglow #542](https://github.com/tolgraven/tolglow/issues/542), [Room Film pass](https://github.com/tolgraven/tolglow/blob/c1fcdb9cffcf9329e736f29cd1cbe2efcce0cc8d/js/preview/film.js), [MetalFX spatial scaler](https://developer.apple.com/documentation/metalfx/mtlfxspatialscaler)

## Run on a physical Mac

Use macOS 13 or later with an Xcode SDK that includes MetalFX. The script compiles the Metal shader through the device at runtime. Keep the Mac on one power setting, repeat the run at matched settings, and save separate directories for each run.

```sh
./run.sh mobile sdr 240 both results-mobile-sdr > mobile-sdr.log
./run.sh all all 240 both results-all > all.log
./run.sh mobile sdr 240 portable results-portable > portable.log
```

The program prints the Metal device, capability query, selected routes, OS and build tools, source hashes, exact formats and dimensions, and setup costs. `both` attempts MetalFX only when the selected device reports support. Descriptor rejection at an individual raster and format logs a skipped route and retains the baseline. `portable` exercises the standalone bilinear route. The production Portable setting is a separate mounted Room acceptance case. [MetalFX configuration](https://developer.apple.com/documentation/metalfx/mtlfxspatialscalerdescriptor)

## Read the results

- `resident_gpu` uses the completed scale-only command buffer’s GPU timestamps. `resident_wall` starts on the CPU before command-buffer creation, includes encoding, submission and waiting, and ends when the GPU output texture is ready. The source upload, pipeline creation, readback and display are outside these timings. Each route warms 40 frames, then reports p50, p95 and p99 in milliseconds. The routes share a queue and alternate order. The fixed two-frame sequence exercises both route orders for each frame. Missing GPU timestamps are counted and printed as unavailable when there are no valid samples. [GPU command timing](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpuendtime)
- `readback_gpu` and `readback_wall` time a separate, warmed private-texture-to-shared-buffer blit. Wall time includes readiness for CPU access. CPU pixel inspection, PNG encoding and app-boundary sharing are separate costs. The repeated copy is from the completed resident texture and reports its padded byte count. Use the paired measurements as separate distributions because real presentation can overlap work.
- SDR uses linear RGBA8, and HDR uses linear RGBA16F with highlights above 1. The synthetic reference evaluates the same scene directly at the output raster in FP32. Each route reports linear RGB MAE and RMSE, MAE over reference shaft interiors, peak, and the number of RGB values above 1. The two PNG phases show the input motion and are encoded for SDR viewing. HDR PNGs use one fixed preview tone map across the reference and both routes. The logged metrics use the original linear HDR values before tone mapping. [Spatial color processing](https://developer.apple.com/documentation/metalfx/mtlfxspatialscalercolorprocessingmode)

The Linux check compiled the analytic scene with GCC and evaluated both phases and color ranges at all five unique raster sizes. At 2806 × 1260 the reference yielded 37,967 and 37,652 shaft-interior pixels in its two phases. Its HDR channel counts above 1 were 230,029 and 234,696. The launcher passed Bash syntax validation and returned its unsupported-platform status. Mac framework compilation, GPU timings, scaled output quality and physical Room presentation require the device run.

## Qualify an actual Room handoff

1. On a physical M4 and a newer Apple-silicon system, retain the signed app build identity, source revisions, OS, GPU, power state, display refresh, HDR mode, and original stills and motion clips. Lock the internal and backing rasters, camera sequence, source sample IDs, rig, fog, exposure and postprocessing settings before comparing each scaler. The existing packaged app receipt covers the WebKit graphics path. [Packaged Room qualification](https://github.com/tolgraven/tolglow/issues/493)
2. Compare the mounted WebGL Room and the experimental native Room with native bilinear and native MetalFX at the same rasters. Report scene and scale GPU times, CPU submission and waits, frame age and drops, and p95 completed presentation interval and fresh presentation rate. Count unique scene frames at the display boundary and retain display refresh separately. Use a common display-resolution reference and inspect thin shafts, moving heads, fresh and standing fog, sculpt glass, rapid cue edges and camera movement in SDR and on an HDR display. Keep the spatial result separate from any future temporal scaler. Temporal qualification needs valid motion and depth, explicit resets on cuts and stale history, and measured fog ghosting. [Room measurement protocol](https://github.com/tolgraven/tolglow/blob/c1fcdb9cffcf9329e736f29cd1cbe2efcce0cc8d/docs/performance/browser-room-device.md), [Apple spatial and temporal guidance](https://developer.apple.com/videos/play/wwdc2022/10103/)
3. If the native renderer owns a drawable, measure its resident presentation directly. For a shared-surface design, measure the real producer-to-consumer path. Record allocation and format compatibility, surface import, GPU/CPU copies and bytes, synchronization, color conversion, queueing and completed consumption. A same-process readback cannot establish this cost. Treat each boundary as measurable even if it uses IOSurface. Exercise the mounted Portable override and confirm the lighting interpolation, 40 Hz DMX publication, and committed packet bytes against a matched show run. [IOSurface](https://developer.apple.com/documentation/iosurface), [Tolglow #542](https://github.com/tolgraven/tolglow/issues/542)

## Native tile-local experiment

Use the same attachment layout, per-pixel math, raster, formats and sample count for a split-pass reference and a fused Metal render pass. Start with opaque scene color/depth and a same-pixel composite that can consume compatible attachment data in its owning pass. Use a fragment attachment read or tile shader to consume transient values while they are in tile memory. Scratch attachments can use memoryless storage and a discard store action when no later pass reads them. Store the resulting color or depth if a later consumer needs it. Room’s depth-aware fog upsample samples neighboring depths, so it needs texture-backed depth at that seam. Keep volume ray integration, bloom, and other stages that sample neighboring pixels on their required texture paths. [Room fog composite](https://github.com/tolgraven/tolglow/blob/c1fcdb9cffcf9329e736f29cd1cbe2efcce0cc8d/js/preview/fog.js), [Apple tile-based deferred rendering](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering), [Memoryless storage](https://developer.apple.com/documentation/metal/mtlstoragemode/memoryless)

Capture the split and fused passes on each physical GPU. Compare attachment loads and stores, external-memory bytes from available counters, GPU p95, and completed mounted presentation cadence under identical fog and postprocessing. Verify color and depth dependencies with matched captures before extending the fused pass. The existing WebGL pipeline includes opaque scene rendering, fog, Glass, bloom and final Film stages. Its optimizations have their own experiments. [Room pass order](https://github.com/tolgraven/tolglow/blob/c1fcdb9cffcf9329e736f29cd1cbe2efcce0cc8d/js/preview/scene-renderer.js), [WebGL #489](https://github.com/tolgraven/tolglow/pull/489), [WebGL #535](https://github.com/tolgraven/tolglow/issues/535)
