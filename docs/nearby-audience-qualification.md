# Measuring audience participation at a venue

The [operating guide](nearby-audience.md) covers enrollment and mapping. This run measures what changes between a single dancer and a crowded room. Record the app revision, gateway model and OS, participating device models, zone layout and whether each run uses the Clip, full phone app or Watch. Record aggregate counts and timing. A camera recording or an individual pulse history is unnecessary for these measurements.

## Test the Clip before distribution

The simulator, local iPhone rehearsal and public download answer different questions. Development of the lighting engine, Studio, BLE gateway and phone UI can proceed independently of App Store enrollment.

### Run the guest UI in the simulator

On a Mac with Xcode and XcodeGen, run `xcodegen generate` in `native/`, open `Tolglow.xcodeproj`, choose **TolglowAudienceClip** and run on an iPhone simulator. This launches the guest UI without a signing team or domain. To test the invitation handler, edit that scheme’s **Run → Arguments → Environment Variables**, add and enable `_XCAppClipURL`, and paste the exact stage URL printed by the bridge. Xcode supplies it to the Clip as a browsing-web user activity. A direct scheme launch skips the system App Clip card. The automated capture installs and opens the actual Clip. Bluetooth enrollment and lighting output require a separate rehearsal. [Apple’s testing guide](https://developer.apple.com/documentation/appclip/testing-the-launch-experience-of-your-app-clip) · [Simulator capture script](../native/Tests/capture_audience.sh)

### Scan a local stage QR on an iPhone

1. Start the bridge with an HTTPS test origin such as `https://stage.example`. Keep it running and use the QR and the exact `/audience/<64-lowercase-hex-fingerprint>` URL it prints. The key is created for that run.
2. Connect a test iPhone to Xcode, enable Developer Mode on the phone if prompted and **build and run the Clip scheme on that phone** so iOS caches a device-signed Clip. Use the bundle ID from the signed Clip target. Local Experiences accept development, ad hoc and TestFlight builds. Device signing must support the target’s entitlements. A free Apple Account can provision some apps through Xcode’s Personal Team, but advanced capabilities depend on the team and profile. The existing unsigned simulator build is immediately usable if device signing is unavailable. [Apple’s developer account overview](https://developer.apple.com/help/account/basics/about-your-developer-account) · [Apple’s device testing steps](https://developer.apple.com/documentation/appclip/testing-the-launch-experience-of-your-app-clip)
3. On that iPhone open **Settings → Developer → Local Experiences → Register Local Experience**. Enter the exact printed URL (or its matching stage URL prefix), the Clip’s signed bundle ID, a title, subtitle, header photo and an action such as **Open**. Scan the QR using **Code Scanner** in Control Center, check the card and open it. Apple permits local QR, NFC and App Clip Code invocations without configuring Associated Domains, hosting an AASA file or owning the example domain. This registration applies to that test phone. [Apple’s local experience instructions](https://developer.apple.com/documentation/appclip/testing-the-launch-experience-of-your-app-clip)
4. Allow Bluetooth, join the invited stage and tap once. Check the stage count and the receiving show’s accent cue. A second phone needs its own signed build and Local Experience for this path. Remove the local registration before testing an App Store Connect experience because the local registration takes precedence. Verify the installed parent app separately using a Universal Link. [Apple’s launch verification](https://developer.apple.com/documentation/appclip/testing-the-launch-experience-of-your-app-clip)

### Publish invitations for guests later

**Apple-hosted default link.** After uploading the full app with its embedded Clip and configuring a default App Clip experience in App Store Connect, Apple generates a link that works on iOS 16.4 or later. That link can be used in a QR without a venue-owned web server. Apple supports optional query parameters. Tolglow currently extracts the stage fingerprint from the HTTPS path `/audience/<fingerprint>`. An Apple `/id` link has a different path and the shipped Clip presents an invalid invitation for it. Supporting a generic stage picker from that link or carrying a validated fingerprint in an Apple-link parameter remains separate client work. [Apple’s default link instructions](https://developer.apple.com/help/app-store-connect/offer-app-clip-experiences/offer-a-default-app-clip-experience/) · [Tolglow’s invitation handler](../native/AppClip/TolglowAudienceClip.swift)

**Custom stage QR with a pinned room.** Enroll for App Store distribution, record the Apple Developer Team ID, select that team for signing and register the actual parent and related Clip bundle identifiers. The Clip’s identifier extends the parent’s. Set `AUDIENCE_DOMAIN` on the signed targets to the HTTPS host you control. Use the identifiers from those signed builds when creating the AASA document, including their actual app identifier prefix, which usually matches the Team ID. The repository’s domain and bundle ID settings are build defaults. [Apple’s App Clip registration](https://developer.apple.com/help/account/identifiers/register-an-app-id-for-app-clips/) · [Project settings](../native/project.yml)

Serve `/.well-known/apple-app-site-association` over HTTPS on that host. Put the signed Clip app identifier in `appclips.apps` and the signed parent identifier in `applinks.details` matching `/audience/*`. The app and Clip need `appclips:<host>` in their signed Associated Domains entitlement, and the parent needs `applinks:<host>` for Universal Links. Archive the app with the embedded Clip, check Apple’s size limit for the planned invocation, upload it, and configure the default experience and the advanced URL prefix that covers the stage invitations. In App Store Connect check domain validation, submit the build and experience as required for review and release, then scan from a fresh phone. [Apple’s domain association guide](https://developer.apple.com/documentation/appclip/associating-your-app-clip-with-your-website) · [Advanced experiences](https://developer.apple.com/help/app-store-connect/offer-app-clip-experiences/offer-an-advanced-app-clip-experience)

For the public-download measurement, start with a phone that has never installed the parent app, remove local test experiences and provide cellular internet for the first download. Scan the venue QR, open the Clip, allow Bluetooth, tap a step and observe an accent at the show. While the Clip is installed, repeat on an isolated stage with Wi-Fi and cellular data disconnected and Bluetooth enabled. Repeat with the parent installed to verify that the same invitation opens Dance floor there.

## From a QR scan to a lighting cue

Place two stages with distinct keys within range. Try both stages from the same QR. Only the invited key should be accepted. Scan a second invitation while joined, then scan it twice. Record which stage actually receives the next tap. Stop sharing and verify the count returns to zero. With a running stage session, measure time from the last accepted packet until the host drops that contribution. The gateway participant expiry and the show’s independent gateway timeout cover different failures.

## Measure motion and step timing

Start with one guest and disable musical cooldown on a rehearsal accent cue. Record the expected and received counts for a known sequence of taps. Repeat for in-place dancing, a pause, people crossing the camera view, phone motion, paired Watch and a Watch-only stage connection when that build is available. Compare camera- and wrist-detected onsets against the same independent count. Report missed and extra steps separately. Restore the intended musical cooldown for performance.

For end-to-end latency, film a visible tap or step and the responding fixture in the same high-speed capture. Convert the frame difference to milliseconds using the **actual capture frame rate**. Record sample count, median, 95th percentile, maximum and camera frame duration. This avoids subtracting clocks on different devices. Test both the fresh cue onset and a low-amplitude sustained effort change. A level sent five times a second and a step event can have different latency.

## Grow and shrink a crowd

Start with one guest, grow to the available crowd and return to one. Log the actual number of participants at each plateau. Vary the distance, number of people between guest and gateway, and number of gateways individually. Drive a known cue from one zone and another cue from the second. Arm, exclude and unplug each zone in turn. When the only pulse-sharing guest withdraws, check that the pulse reading disappears while effort from the others continues.

Keep one person active while the others rest. With sixteen participants and one dancer reporting full effort, the expected global mean is approximately 1/16, regardless of which zone the dancer occupies. Record the queue high-water mark, rejected observations, missing cues and time to recover after a gateway is restarted. Leave the stage running with an empty floor for longer than its configured gateway timeout, then return and trigger one accent. An armed, healthy gateway should serve the returning group. Stop the gateway itself and check for a dropout. Distinguish detected sensor steps from successfully delivered cue commands. A counted tap sequence helps separate detector and transport errors.

Use another pass with guest computation explicitly enabled on one full-app device, then several. Record remote jobs accepted before the deadline, local fallback counts, incomplete frames, physical-output differences from the reference show, battery change and thermal state over the same duration. Turn a worker off and verify the participant can continue sending motion. Keep the Clip in sensor-only mode throughout.
