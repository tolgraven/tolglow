# Application-agent tasks

`tolglow.development.agents` owns application editing separately from show-authoring
agents. A task creates fresh paired Tolglow/Afterglow Git worktrees from committed
base references, runs the configured Codex executable through the existing
Docker execution boundary, and exposes bounded progress and actual Git changes.
It never applies its edits to the running lighting application.

## Service contract

```clojure
(def manager
  (app-agents/create-manager
    {:workspaces workspace-manager
     :execute! (terminal/streaming-runner terminal-manager)
     :credential-store credential-store
     :providers {:codex {:credential-ref "credential-<uuid>"
                        ;; :model is optional
                        }}
     :check-profiles [:tolglow-pure :afterglow-pure :studio-build]
     :config-path "/configured-workspace-parent/.tolglow-application-agents.edn"}))

(def task
  (app-agents/start! manager
    {:provider :codex :repo :tolglow :policy :after-turn
     :prompt "Add the requested control and test its behavior."
     ;; Optional refs resolve to committed objects before worktree creation.
     :base-refs {:tolglow "HEAD" :afterglow "HEAD"}}))

(app-agents/status manager (:id task))
(app-agents/read-events manager (:id task) 0)
(deref (app-agents/result manager (:id task)) 1000 :still-running)
(app-agents/cancel! manager (:id task))
```

Construction is inert: no worktree, credential read, executable probe, or provider
request occurs. The host supplies the workspace manager, credential store and
isolated execution adapter. There is no fallback that executes an agent on the
host. CLI and Docker image availability remain the execution adapter's explicit
responsibility; `:execution-configured?` does not mean that either is installed.

The development facade explicitly restores configuration and the issued workspace
catalog during startup. Configuration contains versioned provider metadata and
credential references only; it lives at
`<workspace-parent>/.tolglow-application-agents.edn`. Updates use a private file,
fsync and atomic replacement. Symbolic-link paths, oversized files, trailing EDN
forms and unsupported configuration schemas are rejected. Restoring this file
does not read the credential value or execute a task. New API keys go to the
existing separate credential vault; a failed configuration write removes the
newly issued unused reference.

The Ring API exposes:

| Request | Behavior |
| --- | --- |
| `GET /api/application-agents` | Public provider configuration, task list and explicit capability/runner readiness. |
| `GET /api/application-agents/status?id=...` | Current task, paired workspace, Git summary, checks and candidate. |
| `GET /api/application-agents/events?id=...&cursor=...` | Bounded progress since the cursor. |
| `POST /api/application-agents/configure` | Configure `:codex` with `:api-key` or `:credential-ref`, and optional `:model`; returns no key. |
| `POST /api/application-agents/start` | Start the documented task request on fresh paired branches. |
| `POST /api/application-agents/cancel` | Cancel a task identified by `:id`. |

Requests use the common same-origin middleware and server-runtime identity guard.
They do not enter the lighting frame queue or reset on a show load. The separate
show-authoring chat endpoints continue to act on the live lighting model.

The host's Ring facade should accept only the documented request keys. Roots,
container images, arbitrary command arguments, provider environment values and
check commands are trusted host configuration, never browser task fields.
Task identity is generated by the service. A task's workspace has that identity
and branches named `tolglow-agent/<id>` in both repositories. Existing modified
files stay in their original checkouts; uncommitted changes are not copied into
the new task. Worktrees and diffs remain available after completion or cancellation.

## CLI, credentials and protocol

The fixed adapter uses:

```text
codex --no-daemon -a never exec --json --ephemeral --ignore-user-config \
  --sandbox workspace-write -C <owned-repository> \
  --add-dir <paired-repository> [--model <configured-model>] -
```

The prompt travels over stdin. The configured API key is looked up only when the
worker starts, passed as `CODEX_API_KEY` in the child environment, and never put in
argv or the public task record. The terminal boundary passes environment names
to Docker, rather than embedding values in command arguments. No host credential
directory, unrelated Codex session, or Docker socket is mounted.

`CODEX_API_KEY` is the variable assigned by the official
[TypeScript SDK execution adapter](https://github.com/openai/codex/blob/ddfaef91b258da5a0217951ed5f6e0039add5e02/sdk/typescript/src/exec.ts#L197).
Both the original installed `0.172.0-alpha.2` binary and the image's stable
`0.171.0` binary accepted the exact flag combination with `--help`, returning
exit code zero. A container-version change must repeat that
capability check, particularly `--no-daemon` and `--ignore-user-config`.

JSONL projections follow the official SDK
[events](https://github.com/openai/codex/blob/ddfaef91b258da5a0217951ed5f6e0039add5e02/sdk/typescript/src/events.ts)
and [items](https://github.com/openai/codex/blob/ddfaef91b258da5a0217951ed5f6e0039add5e02/sdk/typescript/src/items.ts)
at commit `ddfaef91b258da5a0217951ed5f6e0039add5e02`:

- Thread and turn lifecycle; bounded agent messages and supplied reasoning summaries.
- Command status and bounded command output; file-change notifications.
- MCP tool name/status, web search, plan items and explicit errors.
- Separate stderr events. Unknown future event types are visible as compatibility
  notices; malformed events make a turn unsuccessful.

A zero process exit alone is insufficient: the stream must include a successful
turn completion, without fatal/protocol errors or truncation. Raw MCP arguments
and results are not retained in the public projection. The known credential value
is redacted from retained events and errors, then removed from private task state
when the task finishes. Arbitrary credentials independently read or written by
agent-generated code are outside this redaction guarantee.

The adapter is for newly owned ephemeral tasks. Claude Code, control of unrelated
desktop sessions, MCP session attachment, and follow-up/resume are not implemented
by this service. Unsupported provider requests fail before worktree creation.

## Progress, ownership and cancellation

Task states are `:queued`, `:preparing`, `:running`, `:checking`, `:completed`,
`:failed`, `:cancelling` and `:cancelled`. Completion of an agent turn and success
of its checks are separate fields: a completed generation with failed checks
has no candidate ready for use.

Reader callbacks perform bounded parsing and memory updates. An independent
observer reads the actual paired Git status at most once per second while the
CLI runs and records changed-file summaries. A final observation runs before
completion. These summaries derive from Git, not the agent's description of its
work. Full diffs and full check logs use the existing workspace endpoints.

The default event ring retains at most 256 events and 512 KiB of encoded event
data. Each event has a monotonic cursor; `read-events` reports history loss through
`:dropped?`, allowing the UI to refresh task status and diffs. Reconnecting resumes the existing task. Agent stdout is bounded to 2 MiB and 64 KiB per
line by the execution request; the default run deadline is five minutes.

One worker is the default, at most two are supported, and four further tasks may
queue. Task history defaults to 32 entries. The workspace manager independently
limits how many paired workspaces it owns. These limits fail explicitly instead
of silently deleting work or growing unbounded queues.

Cancellation while queued prevents worktree/process creation. Cancellation
during execution interrupts the owning runner. If Docker is still copying the
container filesystem, the terminal manager retains that pending creation until
the daemon settles, then removes it; no agent process may start after cancellation.
Its `:pending-containers` status is the cleanup authority, so a cancelled task is
not by itself evidence that a pending Docker filesystem has already disappeared.
Cancellation during post-turn checks interrupts those checks as well.
`:cancelling` remains visible until the task's runner exits. Closing this manager
cancels only its tasks and observer; the host closes terminal/workspace resources
separately. Worktrees are retained for review.

## Policies and current limits

| Policy | Behavior |
| --- | --- |
| `:manual` | Produce edits and a reviewable diff; no checks or code activation. |
| `:after-turn` | Run configured fixed checks, then stage a review candidate only if every required check passed on the current paired fingerprint. |
| `:preview` | Explicitly unavailable; rejected before starting a task. |

Staging records a checked fingerprint. It starts no preview process, merges no
branch, commits no changes, and reloads no live code. A subsequent file change
invalidates readiness through the existing workspace staging rules. Actual
candidate-runtime startup, target-specific hot reload, last-good rollback and
their UI remain separate implementation work.

Application task history is currently runtime-owned. Unlike show-authoring chat,
it is not yet restored from a saved show. Provider references/settings and issued
workspaces now restore independently through the development owner. Recovered
workspaces remain editable and reviewable, but recovering a worktree does not
resume a CLI process or restore an old check approval. Durable task/chat history
and session continuation still need a separate implementation.

## Verification

The focused module suite passed **11 tests / 80 assertions**; the combined module,
new Ring/configuration/runtime host tests and existing development/web tests passed
**22 tests / 157 assertions** after the move to `src/tolglow`. It uses actual temporary paired Git repositories and a real local
fixture process at the isolated execution seam. That process emits source-derived
Codex JSONL and edits a worktree; it is not a recording of a provider run. Tests
cover streamed output before completion, branch isolation, actual diff summaries,
credential redaction, bounded history, malformed/unknown events, failed execution,
cancellation before execution/during execution/during checks, failed checks and
fingerprint-gated candidate staging.
The actual Studio runtime also verifies credential-vault wiring, rejection of a
previous server identity and continued application-agent execution across a
lighting-show restart.

Run:

```sh
lein test tolglow.development.agents-test
```

The explicit Docker fixture gate passed six assertions using image
`sha256:0f3c5dfe1fb584a7afe8ff588e946e8900845b36693b0cfac64ffe56fba6e485`
with network disabled. It traverses the real application-agent/terminal/container
boundary, edits a real paired worktree, streams redacted JSONL and cleans up the
container. The test substitutes only the executable at the IO seam with the
source-derived Python fixture; it does not claim authenticated Codex generation.
It is excluded from ordinary test discovery and can be selected explicitly:

```sh
lein run -m clojure.main -e '(require (quote tolglow.development.agents-test))
      (let [r (tolglow.development.agents-test/docker-smoke!)]
        (prn r) (shutdown-agents)
        (System/exit (if (zero? (+ (:fail r) (:error r))) 0 1)))'
```

Actual provider generation has not been run: it requires an explicitly configured
credential. Source/protocol tests and
CLI `--help` checks are not proof of an authenticated provider turn or a browser
workflow. The Ring facade, top-level runtime callbacks and development lifetime
wiring are implemented and tested; browser workflows have a separate owner and
acceptance gate.


## Following a running task

The Coding agent pane receives `[:development/task-events task-id cursor]` on the operator’s Transit WebSocket. Each update contains up to 16 retained events, the next cursor, and the newest available cursor. Studio reads successive pages after a gap and refreshes the task’s status when history has expired. Closing the pane drops its stream. The task continues in its workspace, and opening the pane again resumes from the last displayed cursor. The final status remains visible after the stream is released.

After building Studio and its local development container, run `lein run -m tolglow.qa.developer-output` to exercise the browser workflow. It uses a local provider fixture, an actual Docker zsh session and a paused show.
